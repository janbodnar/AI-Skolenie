# Prices of AI models

AI model prices may seem complicated at first glance. Providers use multiple  
models, different performance tiers, and separate prices for input, output,  
cached context, or tools. The basic principle, however, is simple: you pay for  
the amount of text and other data that the model processes.

Price lists change frequently. A model may become cheaper, a smaller version may  
be added, or the provider may introduce a cheaper mode for requests that do not  
need to be handled immediately. Therefore, the specific price should always be  
verified in the official price list of the given provider. This chapter explains  
**how the price is calculated**, not one fixed price list.

## What is a token?

A language model does not read text exactly by words or characters. First, it  
divides it into smaller parts called **tokens**. A token can be a whole short  
word, part of a longer word, a space, a punctuation mark, or a combination of  
these elements.

Therefore, the simple rule that one token equals one word does not apply. In  
English, one word is often approximately one token, but numbers, program code,  
specialized terms, and Slovak may consume more tokens. The exact number depends  
on the tokenizer of the specific model.

For common estimates, the unit **million tokens** is used, denoted as **1M  
tokens**. If the model processes only a few thousand tokens, the resulting  
amount can be very small, but in a large application, the differences between  
models multiply quickly.

## Input and output tokens

In APIs, two basic categories are usually distinguished:

*   **Input tokens** – everything the application sends to the model:
    system instructions, the user's question, previous conversation,
    attached documents, and sometimes tool definitions.
*   **Output tokens** – the text that the model generates as a response.
    For models with extended reasoning, internal reasoning tokens may also be
    included in this category, although the user does not see them directly.

Output tokens are usually more expensive than input tokens because the model  
generates them progressively, and each additional token requires additional  
computation. A long answer can therefore cost more than a short question, even  
if the question itself was the same.

One must account for the entire input, not just the last message. If the  
application sends the entire chat history with each request, all previous  
messages are counted again. Similarly, instructions, descriptions of available  
tools, and text of documents attached to the conversation are also counted.

## Basic price formula

The provider usually lists the price per 1 million tokens separately for input  
and output. The total cost of one request can be approximately calculated as  
follows:

$$
cost =
\frac{\text{input tokens}}{1,000,000} \times \text{input price}
+
\frac{\text{output tokens}}{1,000,000} \times \text{output price}
$$

Consider a model with a price of **$2 per 1M input tokens** and **$8 per 1M  
output tokens**. A request contains 12,000 input tokens and the response has  
3,000 output tokens:

*   input: $12,000 / 1,000,000 \times 2 = 0.024$ $,
*   output: $3,000 / 1,000,000 \times 8 = 0.024$ $,
*   total: **$0.048**.

So one request is cheap. However, if the application processed 100,000 identical  
requests, the cost would be approximately **$4,800**. Therefore, when estimating  
a budget, the number of requests and their size are more important than the  
price of a single test.

## What can be charged for?

Tokens are not the only possible item in the price list. It depends on the  
specific provider and model, but we may encounter especially these fees:

*   **Standard input and output:** basic billing for text sent to the model and
    text generated by the model.
*   **Cached input:** repeatedly used part of the input can be stored in cache
    and billed at a lower rate. This is useful, for example, for long system
    instructions that do not change between requests.
*   **Reasoning tokens:** the model may create internal tokens during reasoning.
    Some providers list them together with output, others show them as a
    separate item in statistics.
*   **Images and audio:** image inputs, generated images, speech transcription,
    and speech synthesis may have their own units and prices. An image may not
    be charged as an ordinary text token.
*   **Tools:** web search, code execution, vector storage, batch search, or
    other tools may have a separate fee.
*   **Long context:** some models have a different price or a separate pricing
    tier for very long inputs.

## API: pay-per-use

**API** is an interface designed for embedding the model into your own  
application. The program sends a request and the provider returns a response.  
The account is then billed according to usage, most often based on the number  
of input and output tokens.

In APIs, you usually do not pay for having a chat page open. You pay for  
actually executed requests. This provides great flexibility, but also  
responsibility: the application can send thousands of requests without the user  
noticing immediately.

API is suitable especially when:

*   we want to embed AI into our own program, website, or company system,
*   we need to automatically process large volumes of documents,
*   we want to choose a specific model based on quality, speed, and price,
*   we need custom rules, logging, permissions, and cost control.

When using an API, you need to monitor not only the price list but also **rate  
limits**. The provider may limit the number of requests or the number of tokens  
per minute. A higher limit may require account verification, higher credit, or  
a special contract.

## Cost control and protection against high bills

API providers offer several tools that help monitor and limit usage. Their names  
and exact behavior vary, but the principle is usually similar:

*   **Usage dashboard:** overview of token counts, requests, and money spent by
    day, model, project, or API key.
*   **Cost alerts:** notification by email or other channel when usage exceeds a
    set amount or is approaching the budget.
*   **Soft limit:** notification or recommendation when a certain amount is
    reached. Further requests may continue if the user makes no change.
*   **Hard limit:** a fixed cap after which requests stop or the account stops
    using additional credit. Not every provider offers it as an immediate
    guarantee, so its meaning should be verified in the documentation.
*   **Rate limit:** limits the number of requests or tokens per minute.
    Protects the account from sudden usage spikes as well as infinite loops in
    the program.
*   **Prepaid credit:** using a pre-loaded balance. After it is spent, further
    requests may stop, or credit may be automatically refilled.
*   **Separate projects and keys:** development, testing, and production can
    have separate budgets, permissions, and API keys.
*   **Model permissions:** the team can allow only approved models so that the
    application does not accidentally use the most expensive available option.

An alert is not the same as blocking. An alert may arrive only after requests  
have been processed or with a delay. If it is important not to exceed an exact  
budget, combine the provider's settings with your own control in the  
application.

Your own application can check the estimated price before sending a request,  
track usage per user, and stop further calls after reaching a daily or monthly  
limit. It should also log error retries, because an automatic retry mechanism  
can generate a large number of paid requests when the service is unavailable.

A practical minimum for a production application is:

1.  separate API key for development and production,
2.  set budget and cost alert,
3.  rate limit and maximum output tokens,
4.  logging of usage by model and user,
5.  protection against duplicate requests and unusual activity.

## Subscription: pay for access

With a **subscription**, the user pays a regular monthly fee for access to an  
application, for example a web chat. A subscription usually provides higher  
limits than a free account, access to better models or tools, and priority  
when the service is under load.

A subscription, however, does not mean unlimited usage. It may have:

*   daily or weekly message limits,
*   separate limits for the most powerful models,
*   slower access after exceeding a certain amount,
*   fair usage policies,
*   different conditions for personal, team, and enterprise plans.

Subscription and API are often **two separate services**. A monthly chat  
application subscription does not automatically pay for API requests, and API  
credit does not automatically unlock the paid chat. When working with both  
services, check which service the payment is assigned to.

| Feature | API | Subscription |
| :--- | :--- | :--- |
| Payment method | pay-per-use | regular monthly fee |
| Purpose | custom applications and automation | using a ready-made application |
| Model selection | usually wide, according to price list | according to specific plan |
| Cost control | budget, limits, and logs in the application | plan limits and rules |
| Final cost | depends on number and size of requests | more predictable, but not always unlimited |

## Peak, off-peak, and cheaper modes

Some providers distinguish **when** a request is processed. During busy hours,  
the so-called **peak mode**, the price may be higher or less capacity may be  
available. During less busy hours, i.e., **off-peak** mode, the price may be  
reduced.

An example is **DeepSeek**, which for selected models and usage types offered  
different prices during peak and off-peak hours. Such conditions may change  
depending on the model, region, time, and account type, so do not assume that  
one schedule applies forever.

A cheaper mode may also take other forms:

*   **Batch processing:** requests are processed later, often at a lower price.
*   **Flex or priority mode:** the user chooses between price, speed, and
    guaranteed availability.
*   **Spot capacity:** the price may be lower, but the request may not have the
    same availability as in standard mode.
*   **Volume discount:** a large customer may receive individual terms.

Such modes are advantageous for tasks that do not need to be completed  
immediately: indexing documents, nightly reports, batch translations, or data  
preparation. On the other hand, a real-time user chat requires low latency, so  
a cost-saving off-peak or batch mode may not be suitable.

## Why does one model have multiple prices?

A model is not just one property. Providers adjust the price according to  
several factors:

*   **Model size:** a smaller model is often cheaper and faster, but may not
    handle complex reasoning.
*   **Quality and capabilities:** the most powerful model may have more
    expensive output, higher computational demands, and higher latency.
*   **Speed:** express processing costs more than batch processing.
*   **Context length:** processing an extremely long input may be more
    expensive.
*   **Customer type:** an individual developer, a team, and a large company
    may have different contractual prices.
*   **Competitive pressure:** after the release of a new model, prices of older
    models may drop to remain attractive.

Therefore, it makes no sense to compare only the number next to the "input"  
item. A model with cheap input can be more expensive in practice if it  
generates long responses or requires many repeated calls.

## How to reduce costs

The best optimization starts with measurement. The application should be able  
to record for each request the model used, the number of input tokens, the  
number of output tokens, the response time, and the resulting cost.

The following practices help the most:

1.  **Shorten unnecessary context.** Do not send the entire history with every
    request if a summary or a few last messages suffice.
2.  **Limit maximum output.** A clear request and an appropriate limit will
    prevent the model from generating unnecessarily long responses.
3.  **Use a smaller model for simple tasks.** Classification, field extraction,
    or short summarization often do not need the most expensive model.
4.  **Use cache.** Unchanging instructions or long documents may be billed at a
    lower rate when supported APIs are used.
5.  **Batch tasks.** Off-peak or batch processing may be cheaper if the result
    does not need to arrive immediately.
6.  **Set limits.** Budget, maximum tokens, rate limit, and alerts will prevent
    an unwanted high bill.
7.  **Check for repetition.** A buggy loop in a program can send one request
    thousands of times. Protection against repetition is more important than
    small differences between two price lists.

## Common mistakes

**"I pay for words."** Not exactly. You pay for tokens, and one token may not be  
one word.

**"I only pay for the response."** In APIs, both input and output are usually  
billed. An extensive conversation history can be expensive even when the  
response is short.

**"The monthly subscription includes the API."** The chat application and API  
often have separate billing.

**"The cheapest input means the cheapest service."** Also consider the output  
price, response length, reasoning tokens, repeated calls, and tools.

**"Last year's price still applies."** Price lists change. The provider may  
change the price, model name, limits, and off-peak mode conditions.

## Chapter summary

*   AI models in APIs are most often billed based on the number of input and
    output tokens.
*   Input includes not only the question but also system instructions, history,
    documents, and tool definitions.
*   Output is usually more expensive than input, and in reasoning models,
    internal reasoning tokens can also increase the price.
*   API means pay-per-use, while subscription pays for access to a ready-made
    application and a specific plan.
*   A subscription does not automatically include the API, and API credit does
    not necessarily include the chat.
*   Peak, off-peak, batch, cache, and volume discounts can significantly change
    the final price. DeepSeek is an example of a provider that used different
    prices during peak and off-peak hours for selected models.
*   When comparing, look at the entire request, not just the price of one token.
